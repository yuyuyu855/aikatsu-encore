# 弾の追加とカタログ更新の運用

本人を管理者とし、公式の新弾情報を確認した時にカタログを更新する。小規模な身内利用では、
リポジトリで管理する弾別JSONをアプリと一緒に配布する案を推奨する。
この文書は今後の実装方針であり、弾別JSON、取込ツール、弾切替はまだ実装していない。
常時スクレイピング、cron、画面を開くたびの公式サイト取得は使わない。
メタデータはアプリに同梱する。将来、公式画像の直接参照を採用する場合は画像表示に外部接続が必要。
現段階は画像なしでも番号・名前で使える設計とし、画像の取得・配布・キャッシュ方針は別に決める。
画像の大量取得や転載は本タスクでは実施していない。

## 情報源と版の区別

ユーザーが提示した第1弾の公式URL:
https://dcd.aikatsu.com/encore/cardlist/?search=true&series=629001&display=1&sort=1

`629001` はこのURLにある `series` の値であり、第2弾・第3弾のIDを連番と推測しない。
新弾ごとに本人が公式の弾選択URLを渡す。HTMLの項目・件数・ページ分割規則は未検証で、
第三者JSONは照合候補としてのみ扱い、公式検証の代わりにしない。85件を固定の期待値にしない。

| 概念 | 意味と更新条件 |
| --- | --- |
| `GameSet`／`setId` | 第1弾などの収録範囲。アプリ内部のIDと公式 `sourceSeriesId` を分離する |
| `catalogVersion` | 配布カタログの版。新弾追加と同弾の訂正で更新する |
| バックアップ `schemaVersion` | 所持・譲・求のファイル形式。カード追加だけでは変えず、現行v1を読める状態を保つ |

配置候補は `packages/catalog/data/sets/<internalSetId>.json` と
`packages/catalog/data/manifest.json`。既存のファイルやパッケージではない。
manifestは `setId`、`title`、`sourceStatus`（`unpublished`／`available`）、
`coverageStatus`（`unimported`／`partial`／`complete`）、
`officialSourceUrl`、`sourceSeriesId`、`lastCheckedAt`、`catalogVersion` を持つ案とする。
公式情報の公開状態とアプリの収録範囲を区別し、ゲーム稼働開始日からどちらも推論しない。
必要なら取得日・元データのhashも記録する。

カードは不変の内部ID、表示番号、名前、レアリティ、パーツ種別、出典と検証状態を持つ。
ブランドは確認できた時だけ追加する。画像URLも任意とし、公式への直接参照の利用条件・可用性は別に検証する。
名前・レアリティ・画像ファイルのsuffixが変わっても内部IDを変更しない。
現サンプルの `e1-01`／`e1-02` は永久に維持し、公式照合後の表記訂正でIDを作り直さない。
再録は公式番号・variantと物理カードの識別を検証して別Card IDの要否を判断する。
同じコーデ・商品としての同一性とは分け、未確認メタデータから再録の同一性を決めない。

## 更新の手順

1. 本人が新弾、または同弾の訂正を確認し、公式の弾選択URLを渡す。
2. GPT-6.1-sol担当が将来の取得ツールを実行し、出典付きのstaging JSONを生成する。
   公式HTMLをローカル保存して入力する代替案も用意するが、parser実装には実HTML構造の確認が必要。
3. 必須項目、重複、件数変化、番号の衝突を検証し、追加・訂正・掲載消失の差分をPMへ提出する。
   空、必須欠落、想定外の大減少、少量の不足でも削除が生じる候補は自動反映せず止める。
4. PMが差分と根拠をレビューし、GPT-6.1-sol担当が本人管理のカタログの版を更新して通常のcommit／pushで配布する。
   この文書自体の変更もcommit／pushして履歴に残す。公式データの取込みは本作業では行わない。
5. 利用者は更新前にJSONバックアップを保存し、アプリの全タブと開発サーバーを終了する。
   自分のPCのリポジトリルートで以下を実行する。WindowsのPowerShellでも同じコマンドを使える。

```sh
git pull --ff-only
pnpm install --frozen-lockfile
pnpm build
pnpm dev
```

同じブラウザで `http://127.0.0.1:5173` を開く。再起動・reloadで同じIndexedDBを使う。
本番ビルドを使う場合は `pnpm build` で生成物を更新する。これは公開・配信コマンドではない。
現手順は [README](../README.md) と [ローカル開発](local-development.md) に合わせる。
友人は当面git pullで更新し、将来はURL配信を検討できる。今回APIや課金プロバイダーは決めない。

## 所持データを消さない更新

カタログと個人の在庫は別のデータとして管理する。追加カードの在庫未登録は0相当で表示するが、
既存の保存状態を表示中のカタログmapで作り直して置き換えない。
全ての過去IDを維持する登録簿と、選択弾の表示対象を分離し、在庫は全登録IDに対して保持する。
新カードを加える時は既存データを保ったunionとし、`owned`／`offered`／`wanted` を変更しない。

掲載消失は削除ではなく `retired` などの状態・通常一覧の非表示で扱い、所持と将来の履歴を保持する。
通常のカタログ更新は、利用者が明示確認するバックアップの全置換復元とは別操作とする。
旧v1バックアップを新弾取得後に復元すると、ファイルにない新弾在庫は0へ全置換される。
確認プレビューで対象と変更内容を具体的に示す。通常のカタログ追加ではこの全置換を行わない。
未知IDを含むバックアップや、新しい在庫を古いカタログのアプリが読む場合は安全に停止して説明する。
無言で未知IDを捨てたり、データをresetしたりしない。新しいカタログへの更新を案内する。

現行の [保存層](../apps/web/src/storage.ts) は `normalizeInventory` でサンプル2件をmapし、
[domain検証](../packages/domain/src/index.ts) は未知のカードIDを拒否する。
これをそのまま弾ごとの小さい一覧へ流用すると、別弾の在庫消失や読込停止につながるため改修が必要。
検証には全過去IDの登録簿を使い、表示弾の変更では保存スナップショットを変えない。

DB名 `aikatsu-encore-local`、STORE `state`、key `inventory` と通常利用のオリジンを維持する。
ホスト名やポートを変えると別保存先になるので、更新のために変更しない。
バックアップv1の互換を保ち、将来 `catalogVersion` を任意の補足情報にしても、項目のない旧v1を読み込めるようにする。

## 分母と公開前の確認

弾別・全弾とも、対象収録ID集合内の `owned > 0` のユニークID数を所持種類数とし、
分母はその対象集合のID数にする。複数枚は種類数を増やさず、同じIDの複数弾掲載は全弾で二重計上しない。
検索・所持状態の絞り込みでは分母を変えず、弾・プロモなどの収録範囲の選択でのみ変える。
部分収録は「収録済み範囲」と明記し、100%が公式全件収集を意味する表示にしない。プロモはカテゴリを分ける。
公開前に番号の衝突・必須欠落・重複・空データ・想定外の大減少を候補で止め、
メタデータ訂正の差分も確認する。失敗時は現在のカタログとDBを保持する。

最初の実装範囲はpackages/catalogの構造、サンプルの固定ID、データ読込、弾絞り込み、動的分母、
既存DBを保つ保存・検証の改修と統合テスト。公式一覧のimport parserはHTML取得後に実装する。
受入テストでは以下を確認する。架空の弾・カードはテスト専用fixtureとし、実カタログに混ぜない。

- サンプル2件から第1弾を追加し、第2弾も追加して、既存の所持・譲・求を保持する。
- 弾の表示切替で全保存状態が不変。名前・レアリティ・画像訂正でも内部IDと在庫が不変。
- 掲載消失をretiredにしても在庫を保持し、partialの範囲表示と分母が一致する。
- 旧v1バックアップを復元でき、未知IDを含むデータは全体を拒否して保持する。
- 不正カタログ更新では現在のカタログとDBを変更しない。
