# プロダクト設計

## 利用シーンと範囲

本人と友人が、入手したカードを検索して枚数を増やし、欲しいカードと譲れる枚数を確認できる。
日本語のスマートフォン向けPWAを計画し、まず手動操作でこの流れと保存・復元を完成させる。
画像の参考UIは機能の根拠にするが、固有ロゴやイラストは流用しない。

| 機能 | 位置づけ |
| --- | --- |
| 名前／番号検索、絞り込み、番号順 | MVP |
| 所持枚数、所持種類率、譲れる枚数、欲しいフラグ | MVP |
| JSON全バックアップ／復元 | MVP |
| 身内への譲求公開と候補閲覧 | 共有希望の回答待ち。仮の基本案 |
| カメラ／写真からのコード読取 | 実物形式を検証できた場合に追加 |
| 読取履歴、店舗・筐体メモ、CSV | 読取導入に合わせた個人機能候補 |
| 「配列」機能 | 意味未確認。実装対象にしない |
| オフライン編集の同期、通知、交換予約・承諾・在庫自動移動 | MVP後の候補 |

公式の組合せメタデータが確認できたら、コーデの不足パーツ表示を将来の候補とする。

## 画面と操作

主な移動先を「カード」「譲求」「設定・バックアップ」とし、読取が成立したら「QR」「履歴」を加える。
カード画面は名前／表示番号検索、絞り込み、番号順、所持種類率を上部に置く。
MVPの絞り込みは所持／未所持／譲／求。カタログを検証できた項目のみ弾・レアリティ・パーツ種別も使う。
カード行は名前、番号、レアリティ、所持枚数と増減、譲れる枚数と増減、欲しい状態を示す。
譲求画面は自分の欲しい／譲れるカードを絞って見る。共有採用時のみ公開設定と友人の候補を加える。

片手で主要操作に届く配置、読みやすい文字と押しやすいボタンを優先する。
所持・譲・求は文字と状態表示を併用し、色だけで区別しない。
現在のローカル版は公式公開107件を収録し、公式由来の表裏画像をGit管理外キャッシュから表示する。未取得でも番号と名前で操作を完結させる。
画像から確認した名称・パーツ・AP・ブランドはHTML由来の情報と出典を区別し、ブランド表示がない場合は未設定を維持する。
分母は選択した弾・全公開カードの収録ID集合とし、検索・状態・レアリティ・パーツの絞り込みでは変えない。カタログが部分取得なら収録済み範囲と明記し、全公式カタログの達成率と誤認させない。

## 数量と履歴の規則

- 所持は整数 `owned >= 0`、譲れる枚数は整数 `0 <= offered <= owned`。
- 欲しい状態 `wanted` は所持と独立し、所持していても欲しいを選べる。
- 重複所持を自動的に「譲れる」にしない。利用者が枚数を指定する。
- 所持を減らすと譲れる枚数を超える場合は、理由と変更後の値を示して明示的な調整を求める。
  確認前に所持も譲れる枚数も変更せず、取消時は元の状態を保つ。
- 所持種類数は対象カタログ内で `owned > 0` のカード数。総所持枚数と区別する。
- 履歴の全消去は履歴だけを消し、所持枚数・譲求を変更しない。

読取を追加する場合、認識結果の確定と枚数への反映を分ける。
連続フレームで同じカードを検出しても、1回の確定操作は1枚だけ反映する。
同じ種類の2枚目は明示的な追加操作で扱う。「記録する／しない」の意味は参考では未確定のため、
本アプリでは「読取履歴を保存する」と明記し、所持登録とは別操作にする案をレビューする。
未対応コードは番号や所持を推測せず、手動検索へ移れるようにする。

## データモデル

| モデル | 主な項目・規則 |
| --- | --- |
| `CatalogCard` | 内部 `id`、表示 `number`、`name`、任意の `rarity`／`setId`／`variant`、出典・`verificationStatus`・画像出典。内部IDを番号から分離し、弾・版が不明なら未確定を表せる |
| `Inventory` | `userId`, `cardId`, `owned`, `offered`, `wanted`, `revision`。利用者と内部IDごとに一意 |
| `ScanHistory` | 任意。`id`, `userId`, `cardId?`, 日時、店舗・筐体メモ。個人専用で生コード保存は原則不要 |
| `SharedOffer` | 明示選択した譲／求、`userId`, `cardId`, 公開対象 `audience/group`, 公開状態。既定非公開 |

カード番号とコード対応は別の検証済みマッピングとして導入し、内部IDの代わりに生コードを使わない。
画像の85件を埋めるための架空データは作らない。カタログ更新と利用者データの更新を分ける。
第三者実装の85件と97枠の不一致は [aikatsu-research.md](aikatsu-research.md) を参照する。
レアリティ付き画像IDを表示番号そのものと扱わず、対象弾・プロモを分けて分母を示す。

## 保存・復元と共有

JSONバックアップは `schemaVersion`、カタログ識別情報、所持・譲求、設定を含む。
履歴を採用した場合は任意で含める。新規のバーコード生値はバックアップや共有へ不用意に含めない。
オンライン復元の所有者はログイン利用者に固定し、ファイル内のuserIdやgroupを権限として信用しない。
公開設定は復元で自動的に有効化せず、利用者が公開項目と相手を再選択する。
復元前にスキーマ・数量制約・重複・カード参照を全件検証し、変更の概要を見せる。
全件の検証に通ったバックアップだけを原子的に反映し、一件でも不正なら一件も書き込まない。
不正データや未対応バージョンでは元データを保ち、不正な項目を捨てて残りだけを取り込まない。
未解決のカード参照は表示して復元を止め、黙って捨てない。CSVは一覧の閲覧用で完全復元は保証しない。

共有希望は回答待ち。仮案は身内のグループに明示選択した譲求だけを公開する方式で、
全所持・履歴・店舗メモの公開は含まない。グループのメンバー以外は閲覧できず、公開を取り消せる。
共有していないデータは公開用のレスポンスへ含めない。交換成立による在庫移動はMVP外。

基本のオンライン共有案ではサーバーを正本とし、MVPの変更はオンラインで確定する。
`revision` による競合は409で拒否し、最新値を再取得して利用者に再操作を促す。
在庫更新・読取登録APIは共通 `operationId` を用い、同じ操作の再送で二重加算しない。
オフライン閲覧キャッシュは任意とし、ログアウト・利用者切替時に非公開データを消す。
PWAの導入はオフライン編集を意味しない。Accessログイン・サーバー同期はネット接続が必要。
オフライン編集と双方向同期は別途設計する。独立した二重正本は作らない。
共有不要の場合の代替案はIndexedDBを正本にして無料静的配信を使い、バックアップで端末移行する。

## 技術境界と未解決の依存

`apps/web` はReact／Vite、`packages/domain` は数量規則・スキーマ・純粋関数、管理はpnpm／TypeScript。
共有が必要なら `apps/api` にHonoを置き、Workersの静的アセットとAPIを単一オリジンで配信しD1に保存する。
Accessの具体的なメール許可を認証候補とし、APIはJWTの署名・issuer・audience・期限を検証する。
サーバーの利用者IDは検証済みclaimから取得し、クライアント指定の所有者を信用しない。
各操作で所有者／グループ権限を検証する。静的アセット利用時に `ctx.access` だけへ依存しない。

コード実形式・番号対応、今後のカタログ更新・画像利用と公開配信の条件、最新の無料枠が導入時の依存事項。
現ローカル版の取得・更新・旧DB保持の実装と操作は [カタログ運用](catalog-operations.md) を参照する。
ブラウザ内読取を優先候補とし、カメラ画像・選択写真をサーバーへアップロードしない。
Access Freeの支払情報要否を含め、無料候補が利用者の条件に合うかを採用前に確認する。
